作品公開部署工作流：GitHub repo 與 Vercel

把 Codex 做出的頁面或小工具，整理成 GitHub repo（雲端專案資料夾），部署到 Vercel production（正式公開網址），並用人工檢查確認可以公開。

這一段放在課程尾聲，定位是「作品公開化的下一步」。前面 90 分鐘先學會和 Codex 梳理工作、產出草稿與檢查表；如果之後要把成果做成可公開瀏覽的頁面或小工具，就照這頁把 GitHub repo（放網站檔案與修改紀錄的雲端專案資料夾）與 Vercel production（正式可開啟的公開網址）串起來。這不是寫程式考試，而是學會把已確認可公開的成果，安全放到一個可開啟的網址。

先把五個常見術語翻成白話

學員不用背指令，只要先知道每個字代表哪一種動作。真正要做之前，都可以請 Codex 用白話再說一次。

repo

雲端專案資料夾。網站檔案、圖片、README 與修改紀錄都放在這裡。

commit

存一個修改紀錄。像幫這次修改拍照，順手寫一句「這次改了什麼」。

push

把本機修改上傳到 GitHub。也就是把自己電腦裡的新版交到雲端資料夾。

pull

把 GitHub 上的最新版拉回來。開始修改前先同步，避免拿舊版本繼續改。

deploy

發布成可開啟的網址。Vercel 會讀取 repo 裡的成果，產生可以分享或檢查的頁面。

不用背流程，要學會怎麼跟 Codex 協作

GitHub、Vercel、瀏覽器畫面可能會因帳號狀態而不同。學員真正要帶走的是問法：先請 Codex 拆步驟、說明會動到什麼、等自己確認後再執行，最後請 Codex 驗證結果。

協作 1說目標

我要做什麼、給誰看、哪些資料可以公開。

協作 2請它拆步驟

先請 Codex 說明接下來會做哪些事，不急著執行。

協作 3確認邊界

會改哪些檔案、會連到哪些外部服務、是否要登入授權。

協作 4一次做一小步

讓 Codex 先做低風險步驟，看到結果再往下。

協作 5看結果再回饋

把自己看到的畫面、錯誤訊息或不懂的地方貼回去。

協作 6請它驗證

要求 Codex 回報網址、截圖、noindex 與仍需人確認的事項。

開場先說目的

這份成果是給誰看、希望別人看完知道什麼、哪些資料可以公開。

先請 Codex 拆步驟

先看它會怎麼安排工作，再決定哪一步可以做、哪一步要先停下來。

遇到登入或公開先停

凡是授權、發布、刪除、外部寄送或付款，都先回到本人確認。

每一步都要看結果

完成後要看得到網址、畫面、檔案清單、檢查結果或仍需人確認的地方。

第 1 步說清楚要公開的成果

主題、資料來源、不能放的內容、希望使用者看到什麼。

第 2 步請 Codex 建頁面

先做本機版本，也就是目前電腦或 Codex 工作區看得到，還不是公開網址。

第 3 步建立 GitHub repo

把網站檔案、README 交接說明與修改紀錄放到雲端專案資料夾。

第 4 步部署到 Vercel

從 Vercel 匯入 GitHub repo，讓網站產生可開啟的正式網址。

第 5 步取得正式網址

取得 production URL，確認網址可在不同裝置開啟。

第 6 步人工檢查後分享

檢查無個資、無內部資料、連結與版面正常。

先確認公開範圍：public 代表任何拿到網址的人都可能看見內容；noindex 只是請搜尋引擎不要收錄的設定，不是隱私保護。

GitHub 帳號

用途是放網站檔案、說明文件與每次修改紀錄。註冊後要完成 Email 驗證，才能順利建立 repo。

GitHub 官方帳號教學

Vercel 帳號

用途是把 GitHub repo 部署成公開網址。建議用 GitHub 登入，匯入 repo 時比較順。

Vercel 官方入門教學

Codex 外掛

外掛是讓 Codex 可以連到 GitHub、Vercel 或瀏覽器檢查的授權能力，不是讓 Codex 自己開公司帳號。

Codex Plugins 官方說明

遇到任何確認畫面怎麼判斷

學員不需要記住每個工具的按鈕，但要養成同一個判斷習慣：先問「會改哪裡、會送去哪裡、能不能復原」。凡是會改檔案、登入授權、公開發布、外部寄送、刪除、安裝、付款或碰到密碼金鑰，都要先停下來請 Codex 說明，再由本人確認。

可以先同意

只讀檢查、整理草稿、產生本機檔案、開本機預覽，且沒有外部傳送或正式資料變更。

先看清楚再同意

會修改檔案、commit、push、啟用外掛、登入 GitHub/Vercel、部署公開頁。

先停下來問人

付款、改公司權限、刪除資料、上傳個資、寄外部訊息、貼密碼或金鑰、連正式系統。

畫面或問題建議怎麼選先停下來的情況
Codex 要修改檔案請 Codex 先說明會改哪些檔案、為什麼改、是否能復原；小範圍教學檔可確認後同意。改到不認識的資料夾、正式資料、多人共用檔，或沒有說明修改內容。
Codex 要刪除或搬移檔案先請它列出完整路徑與原因；確認只是測試檔或可重建檔案才同意。任何正式資料、原始逐字稿、客戶資料、帳務資料、工作成果檔。
Codex 要安裝工具或套件先問用途、安裝到哪裡、是否需要管理員權限；課堂除非必要，不以安裝新工具為優先。要求系統管理員權限、安裝不熟悉軟體、改全域設定或瀏覽器擴充功能。
Codex 要啟用外掛或連接帳號請 Codex 先說明外掛用途與需要的權限；確認是本次任務需要，再依畫面登入授權。要求貼上密碼、token、金鑰，或要求授權不相關服務。
GitHub 要登入或授權用自己的 GitHub 帳號登入；若可以選權限，選「Only select repositories」，只勾本次要用的 repo。畫面要求存取所有 repo、組織管理權限、付款資訊，或帳號不是自己的。
GitHub 要建立 repo練習用可以先選自己的帳號；visibility 不確定時選 Private，要公開展示才選 Public。repo 名稱含個資、客戶名稱、內部案名，或檔案內有未確認資料。
Codex 要 commit / push請 Codex 先列出會提交的檔案與摘要，確認沒有敏感資料後，再同意 commit / push。Codex 沒說會改哪些檔案、要推到不熟的 repo，或包含 .env、金鑰、內部表單。
Vercel 要 Import Git Repository選剛剛建立的那個 repo；不要一次授權所有 repo。練習時選個人或課堂測試 workspace。要選公司 team、正式 domain、付費方案，或畫面看起來不是本次 repo。
Vercel 要 Deploy / Production先請 Codex 檢查公開內容與 noindex；確認後再部署。靜態 HTML 專案通常先沿用預設設定。內容還有個資、內部逐字稿、正式金額，或需要付款、改 domain、改權限。
瀏覽器要求登入、授權或允許權限確認網站網址、帳號是否正確；只允許本次任務需要的權限。要求相機、麥克風、定位、下載、通知、儲存密碼，或登入不明帳號。
要寄 Email、Slack、表單或外部訊息先讓 Codex 只產生草稿，收件人、內容、附件都由本人檢查後再送出。任何外部寄送、群組發文、上傳附件、表單送出、改公開分享權限。
要處理個資、金額、正式資料先做去識別化或只讀檢查，輸出標成草稿或待確認。要下結論、付款、月結、正式核銷、改正式資料庫或公開個資。
要求輸入密碼、API key、token、金鑰不要貼給 Codex 或公開頁；需要時改用官方登入畫面或環境變數管理。任何要求把密碼、簡訊碼、金鑰直接貼到聊天或檔案裡。
付款、升級方案、改 domain 或公司 team課堂不直接操作；先截圖或記下問題，回頭找主管或帳號管理者確認。任何費用、公司設定、正式 domain、權限管理、production protection 變更。
會改哪裡

本機檔案、GitHub、Vercel、公司系統，還是外部服務。

資料會去哪裡

會不會公開、寄出、上傳、分享，或讓其他人看得到。

能不能復原

如果按下去失敗，是否能回到原狀，誰可以幫忙復原。

是否碰到敏感資料

個資、正式資料、金額、密碼、金鑰、費用或公司權限都要先停。

帳號申請時怎麼跟學員說

  1. GitHub 和 Vercel 都可以先申請個人帳號；課堂示範或個人測試通常可從免費方案開始。
  2. 公司正式對外使用時，要確認公司帳號、團隊權限、方案與資料放置規範。
  3. 建立 repo 前先確認公開範圍：public 代表任何拿到網址的人都可能看見內容。
  4. Vercel production URL 代表正式可公開瀏覽；noindex 只是請搜尋引擎不要收錄，不是隱私保護。

要怎麼理解 Codex 外掛

外掛可以先理解成「讓 Codex 看得到或做得到某些事情的授權」。上課不用背外掛名稱，只要確認三件事：這個外掛要用來做什麼、需要登入哪個帳號、啟用後會怎麼驗證。

  • GitHub 類能力：用來建立或查看專案檔案與修改紀錄。
  • Vercel 類能力：用來把已確認可公開的成果變成網址。
  • Browser 類能力：用來實際打開頁面、檢查手機與桌機畫面。

公開前需求說明卡

1. 先說成果要給誰看

  • 主題是什麼，使用者看完要知道什麼。
  • 資料來源是否已確認可以公開。
  • 哪些內容不能放上公開頁，例如個資、內部逐字稿、正式帳務或敏感資料。
  • 先做本機版本，完成後再看手機和桌機畫面。

2. 再確認會留下哪些檔案

  • 先看會被提交的檔案清單。
  • 確認沒有敏感資料後，再建立 GitHub repo。
  • README 要寫清楚網站目的、資料邊界與後續維護方式。
  • 完成後要看得到 GitHub 網址、檔案列表與 README。

3. 發布前先確認邊界

  • Vercel 會把成果變成可開啟網址，發布前先確認內容可以公開。
  • 如果畫面要求 Import、Continue 或授權 GitHub，先確認這是不是本次 repo。
  • 完成後要看得到 production URL 與部署紀錄。
  • review 階段要確認 noindex；正式公開前仍要人工看內容。

4. 最後看公開前檢查

  • 網址是否可在不同裝置開啟。
  • 導覽與按鈕是否能點。
  • 是否有明顯錯字或台灣用語不自然。
  • 是否有個資、內部資料、正式金額或不該公開的內容。
  • 哪些已通過，哪些還需要人工修正。

完成後要交出什麼

  • GitHub repo 網址
  • Vercel production URL
  • 手機與桌機畫面檢查結果
  • README 或簡短說明，寫清楚公開範圍與資料邊界
  • 如果還在內部 review，確認 noindex 已存在
  • 實驗效果記錄：從本機到公開網址花多久、哪一步需要人工登入、公開前修掉哪些風險

公開部署的三個不要

  • 不要把個資、未整理逐字稿、內部表單、正式帳務資料放到 public repo 或公開網址。
  • 不要請 Codex 自行發送外部訊息、付款、變更公司正式系統或處理月結結論。
  • 不要用個人測試帳號承接公司正式對外服務；正式使用前要確認公司帳號與權限。

卡關時查詢

官方文件多半是英文或偏技術；看不懂時，可以請 Codex 摘要成中文步驟，但帳號、授權與權限仍由本人確認。
