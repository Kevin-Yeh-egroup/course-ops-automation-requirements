課程完成品

下課帶走一份真實工作練習包

全班先看一個真實案例怎麼被拆解、溝通與檢查，再把方法套到自己的低風險工作片段。

1. 行政題目

選最常重複、最常漏項，或明天就會用到的一小段工作。

2. 工作流程草圖

寫出什麼時候開始、手上有什麼、誰要確認、最後交什麼。

3. 溝通句型

寫出要怎麼問需求、怎麼說明這只是草稿或檢查清單。

4. Codex 產出

一份草稿、檢查表、提醒清單、異常表或可交接 checklist。

5. 確認清單

標出哪些可修改使用、哪些需要確認、哪些需要補資料。

6. 工具化程度

知道一次性整理、固定做法與分步協助的差別。

開啟完整練習包，可直接照著填需求說明卡、工作流程整理卡與成果檢查表。

使用心智模型

和會執行工作的秘書開會

Codex 不是一次問答就結束。你可以持續補資料、修方向、請它重做，直到成果可以拿來使用。

你負責主持

說明目標、背景、限制、判斷標準與最後要交付的樣子。

Codex 協助執行

整理資料、拆流程、產草稿，列出疑點與下一步。

你負責確認

檢查事實、語氣、風險，以及成果是否能正式使用。

開會方式

先說「我要完成什麼」，再逐步補資料、請 Codex 修改、要求它標出需要人判斷的地方。

完成任務

不是第一次輸出就算完成，而是討論到交付成果可讀、可查、可修、可交接。

需求說明方式

先把工作說清楚：五個問題就能開始

不用先想完整指令。先把工作講清楚，Codex 才知道要整理什麼、要停在哪裡。

1

目的

這件工作最後要幫誰省力？要避免什麼漏掉？

2

資料

手上需要哪些資料？資料在哪裡？

3

流程

平常先做什麼、中間看什麼、最後交付什麼？

4

確認

哪些地方不能猜，或一定要人看過才算完成？

5

輸出

最後要交付提醒、草稿、表格或 checklist？

操作小撇步

七個小撇步

1. 說明情境

現在遇到什麼行政工作？

2. 提供資料

貼上安全範例、副本或低風險素材。

3. 指定輸出

表格、清單、草稿、流程或 checklist。

4. 標出疑點

哪些地方要補問、要人看、要保留判斷。

5. 先拆工作

請 Codex 先整理步驟，再產出草稿。

6. 檢查輸出

看有沒有誤解、漏項或語氣不合。

7. 要求修正版

把修正意見變成下一版輸出。

Agent / Skill 白話說明

方法小抄，以及陪你跑流程的助理

一次性需求

這次先把情境、目的、資料和確認點說清楚，請 Codex 協助整理一版。

Skill

像一張方法小抄：同類工作常常重複，就把固定步驟與檢查方式寫下來。

Agent

像一位有邊界的工作助理：會依流程幫你看資料、整理狀態、提醒要確認的事。

今天先理解

不需要現場建立正式 Skill 或 Agent，先看懂什麼情境可能適合。

什麼時候再討論

同一類工作重複出現、資料來源穩定、確認點清楚，再考慮升級。

打開完整 Agent / Skill 說明頁，用更白話的方式看差別。

四個可選題目

四題都從真實工作拆出來

學員不用四題全做。共同示範後，每個人選最接近自己工作的一題，先看情境與溝通，再照步驟跑一次。

1. 先問真實痛點

這件事做到哪裡算完成？目前最怕漏掉什麼？

2. 說清楚需求

說明目的、資料來源、希望協助的範圍與不能做的事。

3. 拿輸出去溝通

說明這是第一版草稿或只讀檢查，不直接對外送出或改正式資料。

可選題目

日週月報營運雷達、逐字稿內容、名詞/派薪檢查、課程改版包。

課後留下

一份情境說明、一張流程卡、一份可檢查成果。

開啟四個練習操作說明，查看每題的完整情境與操作歷程。

練習 1 營運雷達 練習 2 逐字稿 練習 3 表格檢查 練習 4 課程改版

真實案例一

日週月報營運雷達

一開始看起來只是每天要看很多數字和信，後來發現真正的問題是來源很多：Gmail、Google Ads、好理家在後台、電子報與既有報表都要分層整理。

我要達到的目的

把日報、週報、月報需要看的訊號整理成可檢查摘要，清楚標出已確認、部分確認與待補資料。

平常不用 Codex 時

先看 Gmail，再看 Google Ads 與好理家在後台，最後對照日週月報補上缺口。

我怎麼互動

我先說「我要一份今天可以信任的營運狀態」，再補充哪些來源要分開看。

Codex 幫到哪裡

整理 Gmail、Google Ads、好理家在後台與電子報訊號，產出日週月報草稿。

人要確認什麼

Ads 數字、後台狀態、Gmail 回饋是否需回覆，以及哪些資料只能標成部分驗證。

到練習 1 操作頁

真實案例二

逐字稿變成文章與通知草稿

真實工作不是把逐字稿貼上去就能發文，而是要先知道這份內容給誰看、要放在哪裡、哪些事實還不能直接發布。

我要達到的目的

把錄影或逐字稿變成可審閱的文章素材，並留下哪些已完成、哪些還要確認。

平常不用 Codex 時

先確認素材是否齊全，手動整理重點與草稿，再回管理表更新進度。

我怎麼互動

我先請 Codex 盤點錄影和管理表，不是直接叫它寫文章。

Codex 幫到哪裡

整理重點、改成文章草稿、列出待查證內容，並協助追蹤處理進度。

人要確認什麼

講者原意、人名日期、可公開範圍，以及文章是否能進正式流程。

到練習 2 操作頁

真實案例三

自定義名詞與派薪前檢查

這題不是讓 Codex 判斷薪資，而是把正式動作前的證據整理清楚，讓人知道哪些可以處理、哪些要先停下來。

我要達到的目的

先整理候選名詞、修正對照、事件狀態與派薪前資料，做成可審閱清單。

平常不用 Codex 時

先對照候選資料與既有名詞，整理疑點，正式動作前再請人複查。

我怎麼互動

我先要 Codex 分類和列疑點，不讓它直接新增、關閉或建立薪資。

Codex 幫到哪裡

找出已存在、疑似重複、缺證據與需要人工判斷的項目。

人要確認什麼

是否能新增正式名詞、是否符合派薪資格、是否可以關閉事件。

到練習 3 操作頁

真實案例四

課程改版包

這題就是這份教材本身：從「我覺得不夠真實」開始，一輪一輪把案例、練習頁和簡報改到更像真實工作。

我要達到的目的

讓學員看到真實歷程：需求怎麼說、案例怎麼選、教材怎麼改、哪裡要再確認。

平常不用 Codex 時

先看原教材問題，挑可去識別化案例，手動同步簡報、練習頁與課綱。

我怎麼互動

你先說教材不夠實際，我再回頭找你的工作記錄，整理成可上課案例。

Codex 幫到哪裡

把口語需求轉成改版清單，更新簡報、練習頁、入口頁，並檢查連結。

人要確認什麼

案例是否代表你的工作、是否去識別化、語氣是否適合學員。

到練習 4 操作頁

檢查輸出

看輸出時問三件事

有沒有幫我省整理時間？

資料是否更清楚、待辦是否更集中？

有沒有漏掉重要判斷？

需要人確認的地方是否有列出來？

下次能不能重跑？

情境、資料、流程與檢查方式是否足夠清楚？

效果記錄

用簡單表格留下證據

原本花多久？

估計原本整理、查缺漏、寫草稿需要多少時間。

Codex 幫到哪裡？

記錄省下的整理時間與仍需確認的部分。

下一步怎麼改？

補資料、切更細、固定做法，或暫時維持人工。

可以做到什麼程度

先從可檢查成果開始，不直接跳全自動

1只讀整理

摘要、待辦、缺漏、疑點、補問清單。

2草稿產出

Email、LINE、文章、提醒、分工、SOP 草稿。

3固定做法

同一類工作重複出現時，把步驟與檢查方式留下來。

4分步協助

當流程有多步驟，再考慮讓 Codex 依規則陪你跑一段。

5正式自動化

外部發送、寫回、排程、帳號權限都要另行審查。

課堂重點放在 1 到 4；第 5 階段需要權限、資料安全、責任分工與人工核准，不在第一堂直接操作。

需求說明方式

不要背句型，先把這件事講清楚

我實際跟 Codex 工作時，不是一開始就丟完整指令，而是先說「我想達到什麼」，再看它整理得對不對，接著補資料、切流程、標出要停下來確認的地方。

1先說情境

我現在遇到什麼麻煩，為什麼這件事容易漏。

2說想達到的目的

最後要得到草稿、清單、流程、提醒，還是審閱包。

3補資料與限制

手上有哪些資料，哪些不能公開、不能寫回、不能自動決定。

4看第一版再修正

如果它理解錯，就補充對象、語氣、欄位、流程或判斷依據。

5請它列確認點

最後要看哪些地方仍需要人確認，下一步要問誰或補什麼。

像真實工作一樣來回

第一版通常不是最後答案；重要的是把 Codex 的整理拿來對照自己的工作經驗，逐步補清楚。

不要急著讓它做完

遇到登入、公開、送出、刪除、派薪、正式資料更新，就先停下來，改成列出待確認事項。

課程尾聲延伸

如果成果要公開呈現，走這條路線

不用先背英文指令。先把它想成：把作品放進雲端資料夾，留下每次修改紀錄，上傳到 GitHub，再讓 Vercel 變成可開啟的網址。

repo雲端專案資料夾

放網站檔案、圖片、README 與修改紀錄的地方。

commit存一個修改紀錄

像幫這次修改拍照，附上一句「這次改了什麼」。

push把修改上傳

把本機改好的內容送到 GitHub 的 repo。

pull把最新版拉回來

開始前先拿雲端最新版，避免改到舊版本。

deploy發布成網址

讓 Vercel 把 repo 裡的成果變成大家能開的頁面。

課堂只要聽懂意思；真正操作前，請 Codex 先說會改哪些檔案、會送去哪裡，再由本人確認。

打開完整公開部署教學 先回成果檢查表

帳號與外掛

開始公開部署前，先準備三件事

GitHub 帳號

用來放專案與版本紀錄。註冊後要完成 Email 驗證，才能順利建立 repo。

Vercel 帳號

用來把 GitHub repo 部署成公開網址。建議用 GitHub 登入，匯入 repo 會比較直覺。

Codex 外掛

外掛是讓 Codex 可以連到 GitHub、Vercel 或瀏覽器檢查的授權能力，不是讓 Codex 自己開公司帳號。

先釐清三件事
  1. 這個能力會用來看資料、改檔案，還是連外部服務？
  2. 需要我登入或授權哪個帳號？
  3. 完成後要用什麼畫面或網址確認結果？
學員不用背外掛名稱

只要知道：外掛是讓 Codex 有能力看瀏覽器、連 GitHub 或連 Vercel。真正要確認的是用途、帳號、權限與驗證方式。

看帳號與外掛步驟 看授權怎麼選 回公開部署總覽

確認判斷

看到任何確認畫面，不急著按同意

不只 GitHub / Vercel。只要會改檔案、登入授權、公開發布、外部寄送、刪除、安裝、付款或碰到密碼金鑰，都先停下來問 Codex：會改哪裡、會送去哪裡、能不能復原。

只讀或本機草稿

通常可以先做，例如整理、檢查、產生本機草稿或開本機預覽。

改檔案、commit、push、deploy

先請 Codex 列出會改什麼、送去哪裡，等本人確認後再做。

外部寄送、刪除、安裝、公開

先停下來確認收件人、檔案、公開範圍、是否能復原。

付款、密碼、金鑰、公司權限

課堂不要直接按。截圖或記下問題，找主管或帳號管理者確認。

我會先看

它要改哪裡、資料會送去哪裡、是否能復原。

我會先停

碰到個資、正式資料、金額、密碼、金鑰、公司權限或付款。

看完整授權選擇表 看需求說明卡

公開成果前

把「我要公開什麼」說明清楚

這頁不是要學員背部署指令，而是示範：當成果要變成網址時，先說明公開目的、資料邊界、檢查方式與需要本人確認的動作。

公開目的

這個頁面給誰看？看完要知道什麼？目前是內部 review 還是正式公開？

資料邊界

哪些文字、圖片、表格可以公開？哪些個資、逐字稿、帳務或內部資料不能放？

本人確認

建立 repo、push、deploy、授權帳號、改公開範圍時，都先停下來確認。

公開前檢查

用手機和桌機開頁面，檢查導覽、連結、台灣用語、noindex 與敏感資料。

公開頁可以被轉傳與截圖；review 階段的 noindex 不是隱私保護。

看公開前需求說明卡 回上課入口

課後檢核題

用一份簡報說明你的真實工作案例

請選一件下週真的會做、常重複或容易漏項的工作，做成 5 到 7 頁簡報。對象是同事或主管，目標是讓對方看懂你怎麼溝通、Codex 可以做到哪裡、哪些仍要人確認。

1 真實情境

這件工作是什麼？什麼時候開始？最花時間或最容易漏掉的是哪裡？

2 我要達到的目的

這件工作最後要改善什麼？要避免什麼漏掉或出錯？

3 工作流程

從開始到交付，請拆成 4 到 6 個普通人看得懂的步驟。

4 確認點

哪些資料、語氣、金額、正式動作或對外內容一定要人確認？

檢核重點

案例是否真實｜目的是否清楚｜流程是否能被同事理解｜Codex 協助範圍是否明確｜確認點是否具體。
